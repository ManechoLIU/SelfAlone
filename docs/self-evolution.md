# 老己自我进化记录

- 状态：持续维护
- 创建日期：2026-07-31
- 最近复盘：2026-08-09
- 适用对象：参与老己产品方案、设计、开发和验证的 agent

## 1. 目的与边界

这份文档是老己项目的工作方法和错误预防记录，不是产品需求文档，也不替代 `docs/decisions/` 下的 ADR。

- 产品事实、用户明确选择和架构决策：写入 PRD、技术设计或 ADR。
- 工作过程中的错误、反思、方法论和预防规则：写入本文档。
- 老己项目的完整背景可以保留在本文档中；只有稳定且跨项目适用的原则才同步到 Codex 全局记忆。
- 不记录 API Key、密码、个人隐私、无关项目细节或未经验证的敏感信息。
- 文档可以改善后续任务的检索上下文和行为检查，但不会改变模型参数，也不等同于模型权重自我训练。

## 2. 判断口径

每项工作都要区分以下几类内容，不把它们混成一个结论：

| 类型 | 判定方式 | 文档处理 |
| --- | --- | --- |
| 事实 | 有代码、官方资料、真实接口、测试或用户明确确认作为证据 | 标注证据和验证时间；外部事实可能过期 |
| 用户偏好 | 用户明确表达的体验、范围或协作偏好 | 尊重并记录，但不自动称为最佳工程方案 |
| 假设 | 为推进讨论暂时采用、尚未验证的判断 | 明确标注“假设”或“待验证” |
| agent 建议 | 基于目标和约束提出的方案 | 必须说明备选、取舍、反方风险和推荐理由 |
| 已接受决策 | 用户明确确认或项目负责人批准的选择 | 写入对应 ADR，并标注状态 |

## 3. 任务开始前检查清单

开始实质性方案、设计或开发前，逐项检查：

- [ ] 阅读项目 README、相关 ADR、术语表和本文档的相关错误记录。
- [ ] 用一句话写清用户目标、成功标准和本次不做的事情。
- [ ] 区分已经确认的事实、用户偏好、待验证假设和 agent 建议。
- [ ] 检查当前工作区和已有改动，避免覆盖用户内容或把旧方案当成当前事实。
- [ ] 对本次变更做文档影响扫描，列出需要同步的 PRD、UI 规范、ADR、术语、技术设计和 README。
- [ ] 检查 PRD 的 ASCII 示意、响应式说明和页面规则是否越权固定布局；示意只能核对信息与流程，具体呈现应回到 UI 规范和设计工具。
- [ ] 对有明显取舍的方案列出 2 至 3 个选项，并说明推荐、代价和反方风险。
- [ ] 对每个数据界面分别检查初次加载、真实空数据、搜索/筛选为空、失败和恢复路径。
- [ ] 检查桌面端、手机端和窄屏下的关键状态是否仍然成立。
- [ ] 对第三方服务、模型能力、法律许可、部署限制等外部事实标记验证状态。
- [ ] 先确认领域能力和数据边界，再决定页面导航和视觉表现。
- [ ] 对不可逆或高成本决策明确记录回滚、迁移或验证方式。

## 4. 任务结束后检查清单

准备回复用户或交付结果前，逐项检查：

- [ ] 是否完成了用户真正关心的验收结果，而不只是完成了表面动作。
- [ ] 是否验证了关键行为，而不是只检查文件存在、代码能编译或页面能打开。
- [ ] 是否把已确认决策写入 ADR、把术语变化写入术语表。
- [ ] 是否在同一提交中同步了所有受影响的协作文档，并避免在多份文档维护第二套参数。
- [ ] 是否保留了未解决风险、待验证事项、时间敏感事实和合理假设。
- [ ] 是否存在遗漏的默认态、空状态、错误态、移动端状态或配置入口。
- [ ] 是否有用户指出的错误、方向反转、验证失败或可复用方法需要复盘。
- [ ] 是否把项目特例误提炼成了全局规则，或把全局规则误套回项目。
- [ ] 是否清楚说明没做的事情、未能验证的事情和剩余风险。

## 5. 已沉淀的方法论

| 方法 | 具体要求 | 验证信号 |
| --- | --- | --- |
| 独立论证 | 不把用户提出的方向自动称为最佳方案；先复述目标，再给选项、取舍和推荐 | 回复中能看到反方风险和推荐依据 |
| 结论分级 | 未确认方案使用“提议/待确认”，只有明确批准后才标为“已接受” | ADR 状态与对话确认一致 |
| 决策账本 | 讨论开始前读取已接受决策；已确认内容直接执行，不重复向用户确认 | 新方案只询问真正未决或风险变化的事项 |
| 能力先于导航 | 先定义能力、来源、产物和数据关系，再决定顶层入口 | UI 合并不会导致底层模块或数据被错误耦合 |
| 状态完整性 | 每个外部连接都要设计配置入口、未配置态、验证中、失败态、重试和撤销 | ASCII 图或验收表能覆盖状态，而不是只有成功路径 |
| 能力拆分 | 分开验证文本生成、图片理解、图片生成等能力，不用“多模态”一个词掩盖差异 | 能力矩阵和真实接口验证结果可追溯 |
| 证据纪律 | 第三方能力、接口和合规结论没有证据时保持不确定，不将推测写成事实 | 文档带来源、验证日期或“待验证”状态 |
| ASCII 先行 | 在视觉设计和开发前先画页面、流程和状态的等宽示意图；示意只核对信息与流程，不作为高保真布局要求 | 图中能发现遗漏入口、上下文和默认状态，同时不会限制设计工具的布局与组件方案 |
| 最小化未来抽象 | 为未来保留稳定的能力和数据边界，但不提前建立没有真实用例的空泛平台 | 当前流程简单，未来新增能力不需要重写核心模型 |
| 外部依赖门槛 | 多个外部服务共同组成核心闭环时，先做可行性验证，再投入完整 UI 和外围功能 | 阶段 0 门槛、阶段 1 闭环和发布条件明确 |
| 技能遵循 | 用户明确指定 skill、参考图或文档时，先读取并按其流程工作 | 任务记录中能指出使用了哪些约束和产出 |
| 协作文档一致性 | 每次接受变更先扫描事实源，在同一提交中同步所有受影响文档；PRD 管行为、UI 规范管呈现、ADR 管理由 | 文档引用和版本一致，没有同一规则的两套实现口径 |
| 设计自由度边界 | PRD 只约束能力、内容、流程、状态、文案和验收；导航承载、区块位置、分栏及响应式布局交给 UI 规范和设计工具 | PRD 与 UI 规范不再同时维护固定侧栏、底部导航、面板方向或列数 |
| 空状态五分法 | 所有列表和数据工作区分开设计初次加载、真实空数据、搜索/筛选为空、失败和正常数据 | 页面不会把加载或错误误显示成“暂无数据”，每个状态都有恢复路径 |

## 6. 反复出现的错误模式

| 错误模式 | 常见表现 | 预防动作 |
| --- | --- | --- |
| 过度顺从 | 用户提出方向后立即说“更合理”“就这样定案” | 先给反例和替代方案；结论使用分级状态 |
| 重复确认 | 已经确认的决策在后续收敛时又被当成开放问题询问 | 维护决策账本，回复前扫描相关 ADR 和已确认结论 |
| 过早确定 | 事实、权限或接口尚未验证就写成确定能力 | 标注假设，安排真实验证或官方资料核查 |
| 主流程偏见 | 只画成功路径，遗漏首次进入、未配置、连接失败和撤销 | 建立状态矩阵，逐项补齐默认态和失败态 |
| UI 与架构混淆 | 把两个入口合并就认为后续扩展已经解决 | 单独检查能力模块、数据实体、来源引用和路由边界 |
| 术语偷换 | 把“能看图”称为“能生图”，把“Skill Key”与“AI Key”混为一谈 | 明确输入模态、输出模态、供应商和凭证职责 |
| 未来过度设计 | 为尚未出现的技能建立空的通用平台和复杂导航 | 先解决当前真实闭环，保留可扩展边界即可 |
| 遗漏指定上下文 | 忘记用户提供的 skill、参考图或文档约束 | 任务开始前建立“用户资料清单”并逐项核对 |
| PRD 越权固定 UI | ASCII 图或页面规则把侧栏、底部导航、右侧面板、固定列数写成产品要求，与 UI 规范的设计自由度冲突 | 交付前扫描位置、方向、分栏、断点和组件形态词；保留任务目标与可访问性底线，把具体方案交给 UI 事实源 |

## 7. 初始错误与复盘

### E-20260731-01：对 PPT 入口方案过快顺从

- 日期：2026-07-31
- 场景：讨论是否将读书和 PPT 入口合并。
- 原始判断：用户提出合并后，直接将其表述为“更合理”，并接近定案。
- 发现的问题：没有充分说明 PPT 作为独立产物和未来通用能力时的可发现性、来源扩展和数据解耦风险。
- 用户反馈或验证证据：用户明确指出不应只是顺着意见，应站在 MVP 实现和后续扩展角度反思。
- 根因：把用户的界面偏好误当成工程结论，跳过了备选方案和反方论证。
- 修正后的判断：MVP 界面可以从读书工作区进入 PPT，但 PPT 生成能力和 PPT 作品实体必须独立；书籍只是第一种来源。
- 新增预防规则：所有“合并入口”建议都要分别检查界面、能力、数据、来源和作品可发现性。
- 适用范围：所有产品架构和信息架构讨论。
- 状态：有效

### E-20260731-02：遗漏微信读书 Skill Key 入口和默认状态

- 日期：2026-07-31
- 场景：绘制应用外壳、设置和读书入口的 ASCII 示意图。
- 原始判断：画出了设置页中的微信读书配置，但没有在首次使用和读书同步页面明确表现 Skill Key 的填写入口与未连接状态。
- 发现的问题：用户无法从图中确认微信读书功能如何开始，也无法判断未配置时本地导入是否仍可用。
- 用户反馈或验证证据：用户指出“还缺少填写微信读书 skill key 的地方，以及默认没有填写的状态”。
- 根因：只覆盖了主流程和配置页面，未建立外部连接状态清单。
- 修正后的判断：AI Key 与微信读书 Skill Key 分开；注册后不强制展示配置卡；AI 在已登录主要页面提供轻量、可发现的状态入口，具体位置由 UI 设计决定；微信读书在进入同步入口时就地引导；本地导入不受影响。
- 新增预防规则：每个凭证类集成都必须画出设置入口、功能入口、未配置、连接失败、重试和撤销状态。
- 适用范围：所有第三方连接、授权和配置流程。
- 状态：有效

### E-20260731-03：将多模态与图片生成混为一谈

- 日期：2026-07-31
- 场景：讨论用户只填写一把 API Key 后是否能使用 DeepSeek、Kimi、GLM 的文字和图片能力。
- 原始判断：曾用“支持文字又支持图片生成的多模态模型”作为一个整体问题讨论。
- 发现的问题：图片理解、文本生成和图片生成可能属于不同模型、不同接口和不同权限；一把 Key 也不能跨供应商调用。
- 用户反馈或验证证据：讨论中需要明确用户只配置一套供应商凭证，并区分供应商路由与能力路由。
- 根因：产品语言没有映射到可验证的接口能力矩阵。
- 修正后的判断：用户选择一家供应商和一把 Key；后端按文本、图片理解、图片生成能力检测和路由；供应商不支持生图时使用平台兜底，但不能预先声称三家能力一致。
- 新增预防规则：所有“多模态”结论都拆成输入模态、输出模态、模型、接口、权限和验证证据。
- 适用范围：模型供应商、媒体生成、AI 工具集成。
- 状态：有效

### E-20260731-04：在方案确认前使用接近定案的语气

- 日期：2026-07-31
- 场景：多次将“建议方案”写成“已正式确定”或使用“更合理”的总结语气。
- 原始判断：认为保持对话顺畅比持续保留不确定性更重要。
- 发现的问题：会让用户误以为已经完成决策，增加后续改动成本，也削弱 ADR 的状态可信度。
- 用户反馈或验证证据：用户要求不要趋炎附势，并要求站在实现和扩展角度提出独立判断。
- 根因：缺少显式的结论状态协议。
- 修正后的判断：方案必须标明“提议、已接受、被替代、待验证”；只有用户明确确认或验证完成后才提升状态。
- 新增预防规则：回复和文档中的状态词必须与证据一致，不能用肯定语气代替确认。
- 适用范围：所有需求、产品和技术决策。
- 状态：有效

### E-20260731-05：被用户提醒后才重新接入指定文档技能

- 日期：2026-07-31
- 场景：用户明确指定 `grill-with-docs`，但讨论推进中需要用户再次提醒“别忘记使用这个技能”。
- 原始判断：已理解长期需要文档化，因此认为可以先继续讨论再补流程。
- 发现的问题：遗漏了用户明确要求的工作流程约束，可能导致讨论结果不完整或没有按要求沉淀。
- 用户反馈或验证证据：用户主动提醒必须使用该技能，并要求最终形成方案文档。
- 根因：任务入口没有建立“用户指定 skill 和资料”清单，也没有在每次阶段转换时复核。
- 修正后的判断：用户指定的 skill 在任务开始时读取；其流程约束与项目目标同等重要；阶段转换时重新检查产出要求。
- 新增预防规则：任务开始清点用户提及的文件、skill、参考图和产出格式，并在交付前逐项验收。
- 适用范围：所有带有显式 skill、模板、参考资料或文档要求的任务。
- 状态：有效

### E-20260731-06：重复询问已经确认的 PPT 流程

- 日期：2026-07-31
- 场景：收敛 MVP 方案时，再次询问“是否把用户确认大纲后才生成 PPTX 作为强制流程”。
- 原始判断：把早先已经确认的流程当成尚未决策的候选方案。
- 发现的问题：增加无效往返，说明没有在方案收敛时正确读取和使用已有决策。
- 用户反馈或验证证据：用户指出 PPT 流程之前已经确认，不应再次询问。
- 根因：没有维护并扫描“已接受决策账本”，只根据最近一轮对话组织问题。
- 修正后的判断：已确认的 PPT 流程直接写入 ADR-0009 和 MVP PRD；后续只讨论实现风险或发生变化的部分。
- 新增预防规则：每次提出问题前，先检查相关 ADR、PRD 和本次对话中的明确确认；已接受决策不再重复确认。
- 适用范围：所有持续多轮的产品和技术方案讨论。
- 状态：有效

## 9. 更新与全局同步机制

### 9.1 项目文档更新触发条件

只有以下事件自动追加记录，普通进度不写入：

- 用户指出错误；
- 方案被推翻或出现重大方向调整；
- 测试、真实接口或浏览器验证推翻原判断；
- 同类错误第二次出现；
- 形成可跨任务复用的新方法；
- 一个方法被后续任务验证并升级为正式规则。

### 9.2 记录规则

- 每条复盘都要写根因和新的预防动作，不能只写“下次注意”。
- 事实变化保留验证日期和来源；时间敏感结论不能当作永久规则。
- 新规则与已有规则冲突时，保留旧记录并标注被替代，不静默覆盖。
