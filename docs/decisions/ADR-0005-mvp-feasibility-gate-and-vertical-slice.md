# ADR-0005: 先通过技术可行性门槛，再交付读书到 PPTX 的 MVP 闭环

- 状态：已接受
- 日期：2026-07-31
- 范围：MVP 范围、开发顺序、外部依赖验证、发布门槛

## 背景

老己首版同时依赖微信读书接口、EPUB/PDF 文档解析、跨页精准划线、AI 供应商、图片生成、可编辑 PPTX、注册登录和 Netlify 部署。这些依赖中的任意一个都可能影响核心闭环，直接先做完整 UI 会把不可行性风险推迟到后期。

微信读书同步是用户明确要求的 MVP 硬需求，不能被本地文件导入替代；但在开发前必须验证真实接口、权限、数据字段和商业/合规边界。

## 决策

MVP 分为两个连续阶段：技术可行性验证和产品闭环交付。

### 阶段 0：技术可行性验证

阶段 0 不对外发布，允许使用一次性验证代码或最小实验。必须验证：

1. 微信读书真实测试 Key 能从服务端调用目标接口，并能取得首版需要的书籍、进度、我的笔记以及书友笔记字段。
2. 微信读书 Skill/API 的授权、保存同步数据和商业使用边界已被记录；未确认的合规事项阻止公开发布。
3. EPUB 和文字型 PDF 能提供统一的阅读器外壳与划线抽象；PDF 优先读取内置大纲，没有大纲时尝试从文本层提取章节标题，无法可靠提取时降级为页码导航；文字型 PDF 支持跨页连续选择。
4. PPTX 生成器能输出真正可编辑的 `.pptx`，而不是只生成图片或不可编辑的 HTML 转换物。
5. 至少一家已支持的 AI 供应商能完成文本生成和 PPT 配图路由；DeepSeek、Kimi、GLM 是否可作为可选供应商，必须分别记录验证结果，不能用一家供应商的结果代表全部。

阶段 0 任一硬门槛失败时，停止扩大产品开发，先解决阻塞或明确调整范围；文件导入不能被用来掩盖微信读书硬需求未验证的问题。

### 阶段 1：第一版产品闭环

阶段 1 交付以下端到端流程：

```text
注册 / 登录
      |
      +--> 微信读书同步 ------------------+
      |                                    |
      +--> EPUB / 文字型 PDF 导入           |
                                           v
                                     阅读与精准划线
                                           |
                                     老己笔记
                                           |
                                     PPT 专属对话确定范围和需求
                                           |
                                     AI 生成并编辑大纲
                                           |
                                     导出可编辑 PPTX
```

阶段 1 必须包含：

- 邮箱密码注册和登录；
- 一个当前生效的 AI 供应商和 API Key 配置；
- 微信读书 Skill Key 的独立配置和同步入口；
- EPUB 和文字型 PDF 导入；
- 阅读、精准划线、老己笔记和标签；
- 书籍绑定的 PPT 专属对话、范围选择和需求卡；
- AI 大纲生成、用户确认/修改；
- 可编辑 PPTX 生成和作品再次打开；
- 桌面端和手机端的核心流程。

## 暂不纳入阶段 1

- 养生食谱、专注力管理等后续技能；
- 多人协作、社区、分享和付费系统；
- 复杂阅读统计和社交排行；
- 通用的非读书 PPT 创作工作流；
- 没有真实用例支撑的通用技能工作台。

PPT 在 MVP 界面上可以从读书工作区进入，但其生成能力和作品实体保持独立；书籍只是第一种来源。

## 发布门槛

阶段 1 不能因为页面完成而自动发布。发布前必须有：

- 微信读书接口和合规验证记录；
- 三种声明支持的 AI 供应商的能力矩阵，至少明确文本、图片理解、图片生成和失败降级状态；
- PDF 跨页划线的真实样本文档验证；
- PDF 内置目录读取、章节标题自动提取和无可靠章节时的页码降级验证；
- PPTX 在 PowerPoint 或兼容查看器中的编辑性验证；
- 未配置、连接失败、重试、撤销和本地导入独立可用的状态验收。

## 后果

### 正面

- 在视觉投入前暴露最可能阻塞 MVP 的外部依赖风险。
- 保留微信读书硬需求，同时避免把文件导入误当作替代方案。
- 以一个真实闭环衡量 MVP，而不是以功能列表堆积衡量完成度。

### 代价

- 阶段 0 可能推迟 UI 开发，但能减少后期返工。
- 阶段 1 仍然是较大的首版，需要严格禁止扩展技能和外围系统进入范围。
- 某些供应商能力可能在发布前只能标记为不可用，产品必须显示真实支持状态。
