# SelfAlone 项目协作规范

本文件适用于整个仓库。所有 Agent、设计工具和开发者开始工作前都必须遵循；子目录如需增加专用规则，可添加更近的 `AGENTS.md` 或 `AGENTS.override.md`，但不得静默推翻本文件的产品事实源和安全边界。

## 1. 开始任务前

- 先确认当前工作目录、用户指定文件、附件顺序、硬范围和未提交改动；现有改动默认属于用户，禁止回退、覆盖或顺手整理无关内容。
- 涉及产品、交互、UI 或原型时，先读 `docs/prd/laoji-mvp-prototype-prd.md`，再读 `docs/ui/laoji-mvp-ui-design-spec.md`。普通开发不需要先读历史专项规范。
- 已接受的决定直接沿用；只询问尚未决定、存在冲突或会实质改变结果的问题，不重复确认。
- 对重要方案给出独立判断、替代方案、取舍、最强反方意见和推荐，不因用户提出某个方向就直接附和。

## 2. 唯一事实源

- 产品能力、页面职责、流程、状态、文案和验收：`docs/prd/laoji-mvp-prototype-prd.md`。
- 视觉方向、组件规则、响应式行为和体验验收：`docs/ui/laoji-mvp-ui-design-spec.md`。
- `docs/decisions/` 解释为什么这样决定；`docs/superpowers/specs/` 与 `plans/` 保存专项过程；`docs/self-evolution.md` 保存方法复盘。它们都不能成为与两份主文档并列的实现事实源。
- `prototype/` 是可运行原型。若原型与主文档冲突，先报告并修正文档或原型，禁止自行选择第三种解释。
- 接受产品、交互或视觉变更后，必须在同一任务中做影响扫描并同步所有受影响的主文档、ADR、术语、README、原型和测试；不受影响的文件不机械修改。
- 两份主文档只写当前有效规则，不写日期增量、旧方案、更新日志或“以本段覆盖下文”。历史交给 Git、ADR 和专项档案。

## 3. 产品与设计底线

- 顶层导航只有“对话 / 读书 / 设置”；PPT 从书籍或对话上下文进入，不新增空的通用工作台。
- 共享数据、状态和视觉语言，不共享桌面布局。手机必须按单任务重新组织导航、页头、内容、输入器、键盘和安全区，禁止把桌面多栏、卡片和操作组简单缩窄堆叠。
- “青瓷书斋”保持清新、安静、克制和工作导向。高级感来自真实内容、文字层级、留白、对齐和直接操控；避免大面积水墨、重阴影、巨大标题、装饰性纹样、卡片套卡片和无意义分组文字。
- 正式界面使用成熟图标体系或本地 SVG；不得以 CSS 线框、圆点、字符或占位图标冒充成品图标。图标按钮必须有可访问名称。
- 一屏或一个操作组只保留一个明确主操作。触控目标不小于 44×44px；所有交互有键盘焦点，状态不能只靠颜色表达，并尊重 `prefers-reduced-motion`。
- 所有数据表面必须区分：初次加载、真实空数据、搜索/筛选为空、请求失败、正常内容；加载和失败不得闪现为空数据。
- 异步失败保留用户输入、当前书籍、阅读位置、草稿和已完成结果；禁止过期任务回写覆盖新状态。

## 4. 当前关键业务规则

- 书架卡片只显示包含书名和作者的完整封面；不显示封面下元信息、来源/格式角标、来源筛选、单书删除或回收站。
- 微信读书与本地书共用详情外壳；微信读书不提供站内全文阅读。本地 EPUB/PDF 共用阅读器外壳和阅读控制，格式差异只属于渲染内部。
- 老己笔记只属于当前书籍，不存在跨书籍总入口；用户笔记可编辑删除，引用原文只读。原文操作按上下文出现，不常驻挤压正文。
- 设置首页是聚合页；个人资料、登录邮箱、AI 服务和微信读书使用独立详情页。个人资料只管理头像与昵称；点击头像上传，昵称显式保存；登录邮箱属于账户与安全。
- 普通对话提出 PPT 意图并选定书籍后继续当前会话；只有从书籍详情首次点击“制作 PPT”才创建绑定该书的新会话。
- PPT 范围、需求、大纲和模板选择属于会话草稿；确认模板并点击“开始生成 PPT”后才叫“生成中”，才进入书籍“读书 PPT”列表。
- 桌面在当前会话右侧展开 PPT 工作台；手机进入全屏作品层。大纲是带页边界和文本层级的连续文档；模板显示真实 16:9 封面；生成与预览使用纵向瀑布流，不依赖上一页/下一页。
- 生成进度显示“正在生成第 N / 总页数页”。重新生成产生独立作品，不覆盖旧作品，不提供版本号、“创建新版本”或固定“返回会话”按钮；返回目的地取决于进入路径。

## 5. 文件与实现规则

- 阅读或编辑现有文件前先检查其当前内容；搜索优先使用 `rg` / `rg --files`。
- 手工编辑使用 `apply_patch`；格式化器或可靠的机械批处理可用于纯格式变更。不得用破坏性 Git 命令或删除用户资料。
- HTML 原型按真实页面拆分；共享行为优先复用 `prototype/assets/` 中的 CSS/JS，不在多个页面复制状态逻辑。新增设置详情页复用共享详情壳，一个页面只处理一个主题。
- 不新增生产依赖、不调用付费服务、不上传或发布内容，除非用户明确授权。凭证不得进入聊天、源码、命令参数或日志。
- 只修改用户请求和获批设计范围。发现相邻问题先记录为后续项，除非它直接阻断当前任务。

## 6. 验证与交付

- 按风险运行最小充分验证：目标测试、相关回归测试、链接检查、`git diff --check`、旧规则残留扫描，以及需要时的桌面/移动浏览器视觉检查。
- 原型视觉至少检查 360、390、430、768、1024、1200 和 1440px 中与改动相关的视口；关注横向溢出、内容截断、键盘遮挡、安全区、长文本和 200% 文本缩放。
- 文档变更必须检查两份主文档没有历史标题、覆盖说明、占位符或互相矛盾的规则，并验证页面 ID、状态和链接。
- 未实际运行的测试不得声称通过；原型尚未同步时必须明确标注，不能把书面设计说成已实现。
- 最终回复先说结果，再列关键改动、验证证据和仍存在的真实限制；引用具体文件路径，避免让下一位 Agent 依赖聊天历史。

## 7. Code Review Rules

- 标记任何违反两份主事实源、把移动端做成桌面压缩版、丢失恢复状态、引入重复事实源或未同步协作文档的改动。
- 标记无障碍名称缺失、触控目标过小、仅用颜色表达状态、加载/失败误显示为空、用户输入被清空、异步状态不同源等问题。
- 标记 PPT 草稿提前进入书籍列表、模糊“生成中”、旧作品被覆盖、出现版本管理或固定“返回会话”的回归。
- 对纯格式与 lint 问题优先交给自动化检查；评审文字聚焦行为、数据、安全、可访问性和恢复路径。
