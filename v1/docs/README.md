# 老己产品方案文档

本目录记录“老己”MVP 的产品、领域和技术方案，供后续 agent 和开发者作为共同上下文使用。

## 当前事实源

- 仓库级协作规则：`../AGENTS.md`。
- 产品与交互事实源：`prd/laoji-mvp-prototype-prd.md`。
- 视觉与组件事实源：`ui/laoji-mvp-ui-design-spec.md`。
- 可运行原型：`../prototype/`；认证入口为 `../prototype/laoji-login.html`，登录后产品入口为 `../prototype/laoji-chat.html`，不设置总览快捷页。原型是实现快照，不高于两份主文档；已知差异以 `../prototype/README.md` 为准。

开发 Agent 正常情况下只需先读上述 `AGENTS.md`、原型 PRD 和 UI 设计规范。专项规范、实施计划、ADR 与自我进化文档不是当前实现的必读事实源。

## 按角色阅读

- UI：先读 `../AGENTS.md`，再读原型 PRD 和 UI 设计规范；不要从 ADR 反推具体视觉参数。
- UI 评审：从 `../prototype/laoji-login.html` 或对应独立页面进入；页面映射见 `../prototype/README.md`。
- 开发：先读 `../AGENTS.md`、原型 PRD 和 UI 设计规范；仅在需要理解术语或决策原因时查 `glossary.md` 和 ADR。
- 产品与评审：读原型 PRD、`decisions/` 和 `glossary.md`。
- 产品方法复盘：按需阅读 `self-evolution.md`，普通开发无需读取。
- 技术方案阶段：在 UI 原型评审后再使用 `architecture/`，该目录不属于本次原型 PRD 交付。

## 文档规则

- 已确认的选择写入 ADR，未确认的方案只写在讨论记录中，不伪装成事实。
- 供应商能力、第三方接口和合规条款需要在开发前用真实账号和官方资料验证。
- 变更已确认决策时，新增 ADR 或更新原 ADR 的状态与后果，不直接删除历史理由。
- ADR 负责产品和架构决策；`self-evolution.md` 负责工作方法、错误复盘和预防规则。
- 文档状态使用：`提议`、`已接受`、`被替代`、`待验证`；状态必须与证据和用户确认一致。
- 两份主文档只保留当前有效规则；历史变化保存在 Git、ADR 和专项过程文档中，不写回主文档。
- 同一条规则只在一个事实源中维护：产品行为写入原型 PRD，具体色值、字体、尺寸和组件表现写入 UI 设计规范，ADR 只记录决策理由与后果。
- 原型 PRD 只约束能力、内容、流程、状态、文案和验收结果；导航承载、区块位置、分栏方式、抽屉/面板方向及响应式布局由 UI 设计规范和 Open Design 决定。PRD 中的 ASCII 示意仅用于核对信息与流程，不是布局要求。
- 发生冲突时，行为与状态以原型 PRD 为准，视觉呈现以 UI 设计规范为准；不得在实现中自行选择第三种解释。
- 每次接受产品、交互或视觉变更时，必须先做文档影响扫描，并在同一提交中同步所有受影响的 PRD、UI 规范、ADR、术语或技术文档；不受影响的文档无需机械修改，但评审记录需要说明事实源仍一致。
- 任何列表或工作区新增状态时，都要同时检查初次加载、真实空数据、搜索/筛选为空、请求失败和恢复路径，避免把错误误画成空页面。
